# v0.5.0 项目开发交接

日期：2026-08-04  
当前版本：v0.5.0  
当前数据结构：Schema v13

本文是接手代码时的最短入口。完整业务结论从[文档导航](../00_文档导航.md)进入；当前 Plan 和跨项目报表结构以[Plan 方案与跨项目报表契约](../01_产品与设计/10_Plan方案与跨项目报表契约.md)为准。

## 1. 先把项目启动起来

环境要求：Node.js 20 或更高版本、pnpm 10。首次运行需要在 `src` 目录安装依赖。

普通使用者直接双击项目根目录对应的启动文件：

```text
启动项目测算.cmd       Windows
启动项目测算.command   macOS
```

开发者从项目根目录执行：

```bash
cd src
pnpm install
pnpm start:local
```

启动命令会先构建正式前端，再启动 TypeScript 本地服务，并自动打开：

```text
http://127.0.0.1:4173/
```

正式数据实时保存到：

```text
data/amoya_project_forecast.db
```

几个容易混淆的启动问题：

- 不要直接双击 `output/web/index.html`，正式页面依赖本地语义接口。
- 修改服务端源码后必须重启；普通前端修改也建议重新执行 `pnpm start:local`，确保构建产物最新。
- 如果 4173 端口已有本项目服务，启动脚本会打开现有服务；若被其他程序占用，会明确报错。
- 服务运行时不要同时用外部 SQLite 工具修改 `.db`，重要调整前先用页面“备份”导出副本。
- 旧单 HTML 位于 `output/legacy-singlefile/`，只使用内存 SQLite，关闭前未导出的修改会丢失，不是正式日常入口。

## 2. 目录和代码边界

```text
amoya-project_forecast/
├── src/
│   ├── app/       React 页面、组件和语义 API Client
│   ├── server/    HTTP 路由、应用服务、仓储和 SQLite 文件读写
│   └── shared/    前后端共享契约、领域类型和确定性计算引擎
├── data/          正式 SQLite .db 文件和临时核对数据
├── docs/          需求、设计、原型、验收、计划与交接
├── output/        构建及测试输出，不提交 Git
└── 启动项目测算.*
```

开发时遵守以下边界：

- 页面只调用 `src/app/api/client.ts` 的业务接口，不发送 SQL，也不感知数据库表。
- 服务接口从 `src/server/semanticApiRouter.ts` 进入；事务、仓储和 SQLite 只放服务端。
- 预测、公式、税和现金计算复用 `src/shared/calculation/`，不得在页面或报表里再写一套近似算法。
- `src/app/components/FinancialGrid.tsx` 和 `useGridSelection.ts` 是统一表格与选区交互底座。
- 历史参考项目配置集中在 `src/app/mocks/`，不要把样例金额散落到页面。
- `output/` 是编译结果，任何有效修改都应落回 `src/`。

更完整的数据链路见[项目核心与正式输出契约](../01_产品与设计/08_项目核心与正式输出契约.md)，阶段完成情况见[开发路线与阶段状态](../04_验收与进度/01_开发路线与阶段状态.md)。

## 3. 当前项目设定

- `Project` 是项目主数据，只保存项目编码、项目名称、申报部门和状态。
- `Plan` 是项目下属的独立测算方案，拥有自己的起止期间、参数、预测项、计算批次和事实；当前没有业务 `Version`。
- `Scenario` 当前固定为平台级“基准场景”。`Run` 仅表示一次计算执行记录。
- 项目配置修改先形成草稿实时预览；“保存”只持久化配置，“计算”成功后才更新事实、计算底表和项目报告。
- 报告始终读取最后一个成功批次，不能用尚未计算的草稿替代正式结果。
- 事实坐标是“项目 × Plan × 部门 × 期间 × 场景 × 指标”；同项目不同 Plan 互斥，跨项目查询时不得把同一项目的多个 Plan 无提示相加。
- 业务模块已从数据库和产品中删除，不要从旧原型或历史文档重新引入。
- 金额以十进制字符串保存并用 Decimal.js 计算，不得改为 JavaScript 浮点数直接累加。
- 页面常用期间目前展示 2024-01 至 2030-12；数据库保留更宽底座是为了支持现金回收尾期，不应把全部期间重新堆回主数据界面。

## 4. 最容易改错的地方

1. **Plan 不是全局版本。** 同名 Plan 在不同项目中没有统一业务含义，必须通过项目归属保证组合合法。
2. **实时预览不是正式事实。** 预览和正式计算复用同一引擎，但只有成功计算才能替换 `fact_metric_value`。
3. **派生指标不能直接汇总。** 毛利率需要用聚合后的毛利除以收入重新计算；累计现金流要按期间顺序计算。
4. **保存和计算不是同一个动作。** 计算可以先自动保存，但单独保存不能悄悄刷新正式报表。
5. **兼容单 HTML 不等于正式服务。** 两者共用主要源码和版本号，但数据持久化承诺不同。
6. **Schema v13 当前按开发库重建演进。** 导入旧结构数据库会被拒绝；修改表结构前先确认是否已进入需要正式迁移的阶段。
7. **不要恢复业务模块、Version 或原始 SQL 接口。** 这些都是已明确收敛掉的概念。
8. **临时备份和核对文件标记 `TMP to delete`。** 正式 `.db` 不提交仓库，提交前确认没有误加入用户数据和构建产物。

## 5. 修改后的最小验证

```bash
cd src
pnpm test
pnpm build
pnpm build:legacy-singlefile
```

涉及计算或数据结构时，还要人工检查：

- 五个参考项目可以分别保存、计算并查看报告。
- 不同 Plan 的配置、Run 和事实不串数据。
- 预测项实时预览与正式计算结果一致。
- 项目报表的 POV、行列轴、成员范围和非加法指标正确。
- 数据库备份恢复后，项目、Plan、配置、批次和事实完整。

历史数据核对依据见[六份历史素材回放报告](../04_验收与进度/07_六份历史素材回放与能力覆盖核对报告.md)，当前结构验收见[Schema v13 验收报告](../04_验收与进度/09_Schema_v13_Plan与项目报表验收报告.md)。

## 6. 版本规则

版本号只维护在 `src/package.json`，正式页面和兼容单 HTML 都从这里显示。当前为 `v0.5.0`；后续开发新功能、调整交互或修正计算时，依次更新第三位版本号，例如 `v0.5.1`。不要在组件、文档或启动脚本中建立第二套独立版本常量。
