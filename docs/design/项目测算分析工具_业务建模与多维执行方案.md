# 项目测算分析工具：业务建模与多维执行方案

更新时间：2026-07-26

> 方案演进说明：双层计算逻辑继续保留，但产品界面已进一步收敛。外层改为项目、主数据和跨项目分析；进入项目后拆为“预测配置—计算表格—图表报告”三页；场景比较并入报告。最新界面结构见 `项目测算分析工具_项目中心与预测工具台方案.md`。

## 一、方案结论

产品采用“业务建模层 + 多维执行层”的双层结构，不再把“行项目方案”和“轻量 EPM 方案”视为二选一。

- 财务用户面对业务建模层，用熟悉的行项目、参数、公式、账期和说明完成测算配置。
- 系统通过模型编译层，把业务配置展开为结构化的多维数据。
- 多维执行层统一承载分月损益、现金流、场景、版本和业务板块切片。
- 场景驾驶舱、报告和 Excel 导出读取同一次编译结果，避免各页面重复计算或口径漂移。

这套方式保留了财务人员能够理解的操作方式，同时给后续的版本比较、场景覆盖、分月计算和指标体系留下稳定底座。

## 二、四层计算链路

### 2.1 业务建模层

业务建模层回答“这个项目如何测算”，允许不同性质的行项目采用不同的建模方式：

- 固定值。
- 逐月录入。
- 起始值、目标值和增长规则。
- 单价 × 数量 × 周期。
- 收入或成本比例。
- 引用其他行项目组成公式。
- 账期偏移和分期收付款。
- Excel 或 CSV 导入的外部数据。

项目级定义可用的业务模块清单；每个行项目从该清单中选择归属模块或“公共”，并保留单位、税务口径、生效期间、来源和假设说明，便于财务复核。

### 2.2 模型编译层

模型编译层是业务配置与多维结果之间的确定性转换器，主要负责：

1. 解析参数和行项目依赖。
2. 检查缺失参数、循环引用和口径冲突。
3. 按预测周期展开月份。
4. 将账期规则转换为现金收付月份。
5. 把行项目映射到指标、时间、场景、版本和业务板块坐标。
6. 生成编译运行记录和问题清单。

第一版不开放自由脚本，也不在工具内引入 AI 建模；同样的输入必须得到同样的结果。

### 2.3 多维执行层

第一版建议使用以下维度：

- 项目：作为数据隔离和本地持久化容器。
- 指标：业务参数、收入、成本、利润、现金流和派生指标。
- 时间：年月，默认 12 个月，可扩展至 36 个月。
- 场景：基准、乐观、审慎，以及后续用户复制的新场景。
- 版本：工作版、提交版、定版。
- 业务模块：可选维度，模块清单在项目级定义，行项目保存具体坐标，用于项目内部不同业务组成的分析。

主表采用“行是指标、列是年月”的财务表格形态。场景、版本、业务板块和口径作为切片条件，不强迫用户先理解 Cube 概念。

单元格需要明确区分：

- 输入值：财务可直接维护。
- 公式结果：由指标或行项目依赖计算。
- 场景覆盖：只保存相对基准方案的差异值。
- 派生指标：毛利、毛利率、ROI、净现金流和累计现金流等。
- 锁定结果：已定版版本不可直接修改。

### 2.4 分析与输出层

- 场景分析驾驶舱：比较各场景的收入、成本、毛利、资金占用和现金转正时间。
- 报告审阅：把文本结论、核心假设、主表、驾驶舱图表和检查事项组织成统一报告。
- 导出：CSV 用于明细交换，Excel 使用平台统一模板作为标准交付物。

## 三、持久化与服务建议

正式实现建议采用 TypeScript 单语言服务：

- 前端：TypeScript Web 界面。
- 服务端：TypeScript API 与计算编排。
- 本地存储：SQLite，随服务保存项目、版本、配置、编译结果和运行记录。
- 导入：Excel、单个 CSV 或多个 CSV 作为外部输入源，不直接充当运行期数据库。
- 导出：统一 Excel 模板和按视图导出的 CSV。

SQLite 比散装 JSON/JSONL 更适合版本、依赖、切片查询和一致性更新；同时仍是单文件，便于本地备份和项目迁移。必要时可以补充“项目包导出”，把 SQLite 快照、导入源文件和元数据打包分享。

## 四、原型中的三种布局

原型文件：`docs/prototype/项目测算分析工具_业务建模与多维执行原型.html`

三种布局只改变信息组织，不改变数据、功能或计算逻辑。

### 布局 A：三栏工作台

- 左侧管理项目、步骤和维度。
- 中间并列展示业务建模、模型编译和多维主表。
- 右侧检查当前行项目的公式与多维映射。
- 底部固定展示核心指标。

适合财务日常高频使用，建议作为默认布局。

### 布局 B：上下双层

- 上层突出业务行项目。
- 下层并列展示模型编译和多维主表。
- 右侧保留映射检查器。

业务层和执行层的分界最直观，但同屏横向信息略少，可作为培训或复杂建模模式。

### 布局 C：映射视图

- 按“业务建模 → 模型编译 → 多维主表”横向串联。
- 指标展示区位于底部。
- 省略独立检查器，强调端到端映射关系。

最适合解释系统原理、检查编译链路或做方案演示，不建议替代财务日常主工作台。

## 五、推荐落地方式

第一版以布局 A 为默认日常工作台，同时保留布局 C 作为“模型映射”视图。布局 B 可以等真实用户验证后再决定是否保留。

完整产品流程固定为：

1. 测算工作台：维护业务模型、编译并查看多维主表。
2. 场景分析：在同一结构化结果上比较场景和关键参数。
3. 报告与导出：复核文本、图表、主表和问题，导出 CSV 或统一 Excel。

这意味着产品仍然是财务人员熟悉的测算工具，而不是要求用户直接操作一个通用多维建模平台；EPM 的维度、版本和指标逻辑主要作为内部计算架构存在。
